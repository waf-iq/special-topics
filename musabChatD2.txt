  ---
  What is D2-INT1?

  D2-INT1 is the integration task for Deliverable 2 of the CSAI415 project. It's
  owned by Musab Kamberi and its job is to tie together all the Wave 1 work
  done by the team: once everyone's individual pieces landed (corpus expansion,
  seed scripts, Neo4j loader, Docker infra), Musab runs the full seeding
  pipeline end-to-end to populate all three data stores against the expanded
  corpus.

  ---
  The Project Architecture (context)

  The project is a Hybrid Retrieval + GraphRAG AI agent over scientific PDFs. It
  uses three data stores working together:

  ┌─────────┬────────────────────────────────────────────────────────────────┐
  │  Store  │                              Role                              │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ MongoDB │ Source of truth — stores paper metadata and text chunks        │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ Qdrant  │ Vector database — stores 384-dimensional embeddings for dense  │
  │         │ (semantic) search                                              │
  ├─────────┼────────────────────────────────────────────────────────────────┤
  │ Neo4j   │ Knowledge graph — stores Authors, Papers, Topics and the       │
  │         │ relationships between them                                     │
  └─────────┴────────────────────────────────────────────────────────────────┘

  The data comes from two corpora:
  - SciFact (5,183 scientific abstracts) — used for retrieval evaluation
  - arXiv cs.CL (~150 NLP papers with real author/year/topic metadata) — used
  for the graph and demo

  ---
  What We Did, Step by Step

  Step 1 — Started the Docker stack

  docker compose up -d

  This launched three containers defined in docker-compose.yml:
  - csai415_mongo (MongoDB 7)
  - csai415_qdrant (Qdrant v1.12.4)
  - csai415_neo4j (Neo4j 5)

  Each container has a healthcheck so we know when it's ready to accept
  connections. We waited for all three to show healthy before seeding.

  ---
  Step 2 — Seeded MongoDB

  python scripts/seed_mongo.py --source all

  What it does: Reads data/processed/chunks.parquet (the processed corpus — 49
  MB) and writes two collections into MongoDB:

  - papers — one document per unique paper, with fields: title, authors, year,
  topics, source, pdf_path
  - chunks — one document per text chunk, with fields: paper_id, text, position,
  page_start, page_end, source

  The script uses bulk upsert (ReplaceOne with upsert=True), so it's safe to
  re-run — it won't create duplicates. Topics for arXiv papers are loaded from
  arxiv_batch_meta.json (the full category list, e.g. ["cs.CL", "cs.AI"]).

  Result: 5,338 papers and 15,760 chunks written to MongoDB.

  ---
  Step 3 — Seeded Qdrant

  python scripts/seed_qdrant.py --source all

  What it does: Reads the same parquet file, takes the pre-computed
  384-dimensional BGE embedding for each chunk, and upserts them as vector 
  points into a Qdrant collection called chunks_bge384.

  Each point carries a payload with { chunk_id, paper_id, source, text, title, 
  page_start, page_end } — so the /search API can return full results from
  Qdrant alone without a round-trip to MongoDB.

  The collection uses Cosine distance and an HNSW index for fast approximate
  nearest-neighbour search.

  Result: 15,760 vectors loaded into chunks_bge384.

  ---
  Step 4 — Seeded Neo4j

  python scripts/seed_neo4j.py --source all

  What it does: Reads from MongoDB's papers collection (not the parquet — this
  is the one step that depends on Mongo being populated first) and builds a
  property graph in Neo4j using Cypher MERGE statements (idempotent — safe to
  re-run).

  The graph schema:
  (:Author {name}) -[:WROTE]-> (:Paper {paper_id, title, year, source})
  (:Paper) -[:ABOUT]-> (:Topic {name})

  SciFact papers are skipped because BEIR (the benchmark dataset) ships no
  author metadata — loading them would create orphaned Paper nodes with no
  edges.

  Result: 155 arXiv papers, 764 unique authors, 22 topics, 789 WROTE edges, 306
  ABOUT edges.

  ---
  Step 5 — Verification report

  We created reports/d2_int1_verification.md documenting all the counts above,
  with Musab's name, date, task description, and results table — which is what
  we're about to commit to GitHub.

  ---
  Why This Task Matters

  Without D2-INT1, the three stores exist but are empty. After D2-INT1:
  - The FastAPI /search endpoint (D2-B1/B2) can actually serve queries
  - The Cypher query library (D2-C2) can run against real data
  - The team can demo the full stack end-to-end

  It's the integration glue that proves all the individual pieces work together.
